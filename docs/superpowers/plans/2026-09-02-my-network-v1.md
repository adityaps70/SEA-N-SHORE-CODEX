# My Network v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn Sea N Shore’s existing maritime profile directory into a secure professional social graph with instant follows, request-based connections, blocking, in-app notifications, deterministic recommendations, and relationship-aware Home feed behavior.

**Architecture:** Supabase remains the source of truth. New graph tables and narrowly scoped authenticated RPCs own multi-row relationship transitions; RLS protects all exposed data and block-aware visibility. Next.js server actions validate inputs and call typed Supabase APIs, while focused `network` and `notifications` feature modules drive `/network`, profile controls, Bell notifications, recommendations, and light Home-feed prioritization.

**Tech Stack:** Next.js 16.3.4 App Router, React 19.2.8, TypeScript 5, Tailwind CSS 4, Supabase/Postgres/RLS, `@supabase/ssr` 0.12.5, `@supabase/supabase-js` 2.112.4, Zod 4.5.4, Vitest 4.1.11, Testing Library, Playwright 1.62.1, pgTAP/Supabase DB tests.

**Spec:** `docs/superpowers/specs/2026-09-02-my-network-v1-design.md`

## Global Constraints

- Preserve the fixed product model: Follow is instant; Connect is request/accept; accepting creates mutual follows; unfollow does not disconnect; removing a connection does not force unfollow.
- Blocking removes both follow directions plus any connection/request and prevents interaction until explicitly unblocked; unblocking restores nothing automatically.
- Initial notification types are exactly `connection_request`, `connection_accepted`, and `new_follower`.
- Realtime, email, and push notifications remain out of scope.
- Report/moderation, messaging, endorsements, verification badges, connection notes, 2nd/3rd-degree graph, and ML recommendations remain out of scope.
- Every exposed table must have RLS and explicit grants. Do not expose direct notification INSERT/DELETE privileges to ordinary clients.
- Any SECURITY DEFINER RPC must use `set search_path = ''`, validate `auth.uid()`, revoke default EXECUTE from `public`, `anon`, and `service_role`, and grant only the intended authenticated role.
- Never use user-editable metadata for authorization.
- Do not reveal which side initiated a block. User-facing errors use generic unavailable language.
- Anonymous public-profile behavior stays as it is today; block-aware hiding applies to authenticated viewers.
- Home feed remains broad maritime discovery. Relationship priority is a soft boost, never a connections-only filter.
- Preserve the existing feed cursor shape (`createdAt`, `id`) and calculate the next cursor from the original recency-ordered page, not from the relationship-reordered display array.
- Node runtime floor remains `>=22.0.0`.
- Use the Supabase CLI to generate migration filenames; do not invent timestamps manually.
- No new runtime dependency is required for this release.

- [ ] **Step 4: Implement enums, tables, constraints, indexes, and least-privilege grants**

The migration must create the following schema shape:

```sql
create type public.connection_status as enum ('pending', 'accepted');
create type public.network_notification_type as enum (
  'connection_request',
  'connection_accepted',
  'new_follower'
);

create table public.follows (
  follower_id uuid not null references public.profiles(id) on delete cascade,
  following_id uuid not null references public.profiles(id) on delete cascade,
  created_at timestamptz not null default now(),
  primary key (follower_id, following_id),
  constraint follows_not_self check (follower_id <> following_id)
);

create table public.connections (
  id uuid primary key default gen_random_uuid(),
  user_low_id uuid not null references public.profiles(id) on delete cascade,
  user_high_id uuid not null references public.profiles(id) on delete cascade,
  requested_by uuid not null references public.profiles(id) on delete cascade,
  status public.connection_status not null default 'pending',
  created_at timestamptz not null default now(),
  responded_at timestamptz,
  updated_at timestamptz not null default now(),
  unique (user_low_id, user_high_id),
  constraint connections_canonical_pair check (user_low_id < user_high_id),
  constraint connections_requester_in_pair check (requested_by in (user_low_id, user_high_id))
);

create table public.user_blocks (
  blocker_id uuid not null references public.profiles(id) on delete cascade,
  blocked_id uuid not null references public.profiles(id) on delete cascade,
  created_at timestamptz not null default now(),
  primary key (blocker_id, blocked_id),
  constraint user_blocks_not_self check (blocker_id <> blocked_id)
);

create table public.notifications (
  id uuid primary key default gen_random_uuid(),
  recipient_id uuid not null references public.profiles(id) on delete cascade,
  actor_id uuid references public.profiles(id) on delete set null,
  notification_type public.network_notification_type not null,
  connection_id uuid references public.connections(id) on delete set null,
  created_at timestamptz not null default now(),
  read_at timestamptz
);
```

Add indexes for follower/following lookup, both connection-user columns/status, blocker/blocked lookup, and `notifications(recipient_id, read_at, created_at desc)`.

Enable RLS on all four tables. Revoke all default anon/authenticated table privileges, then grant only SELECT needed by authenticated clients plus `update (read_at)` on notifications. Mutations happen through RPCs, not direct table INSERT/DELETE.

- [ ] **Step 5: Implement private helpers and narrow authenticated RPCs**

Use private helpers such as:

```sql
create or replace function private.network_member_ready(p_user_id uuid)
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select exists (
    select 1 from public.profiles p
    where p.id = p_user_id
      and p.account_status = 'active'
      and p.onboarding_completed_at is not null
  );
$$;
```

and a pair-block check that queries `user_blocks` with elevated internal visibility but returns only boolean state. Revoke helper EXECUTE from `public`, `anon`, `authenticated`, and `service_role`; helpers are invoked only from trusted graph RPC code.

The public RPCs may use SECURITY DEFINER only because they must atomically write notifications and reciprocal relationships. Each RPC must begin by reading `(select auth.uid())`, reject NULL callers, validate caller/target/pair state, and use fully qualified object names with `search_path=''`.

For `accept_connection_request`, implement the transaction in this order:

```sql
update public.connections
set status = 'accepted', responded_at = now(), updated_at = now()
where id = p_connection_id and status = 'pending';

insert into public.follows (follower_id, following_id)
values (v_requester, v_recipient), (v_recipient, v_requester)
on conflict do nothing;

delete from public.notifications
where recipient_id = v_recipient
  and notification_type = 'connection_request'
  and connection_id = p_connection_id;

insert into public.notifications (
  recipient_id, actor_id, notification_type, connection_id
) values (
  v_requester, v_recipient, 'connection_accepted', p_connection_id
);
```

Do not call `follow_profile()` from acceptance because that would generate redundant follower notifications.

For `block_profile`, insert the block idempotently, delete both follow directions, delete the pair connection, and remove pending actionable request notifications for that pair in the same function.

After each public RPC is created:

```sql
revoke all on function public.follow_profile(uuid) from public, anon, authenticated, service_role;
grant execute on function public.follow_profile(uuid) to authenticated;
```

Apply the equivalent exact signature statements for every graph RPC.

- [ ] **Step 6: Add RLS policies for raw graph reads and notification read state**

Connections: authenticated users can SELECT only rows where their `auth.uid()` is either pair member.

Blocks: users can SELECT only rows where they are `blocker_id`; there is no policy exposing rows merely because the caller is `blocked_id`.

export function prioritizeRecentFeedRows<T>(
  rows: readonly T[],
  preferredAuthorIds: ReadonlySet<string>,
  authorId: (row: T) => string,
): T[] {
  const preferred: T[] = []
  const other: T[] = []
  for (const row of rows) {
    ;(preferredAuthorIds.has(authorId(row)) ? preferred : other).push(row)
  }
  return [...preferred, ...other]
}
