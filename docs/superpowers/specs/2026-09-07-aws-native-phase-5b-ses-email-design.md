# AWS-Native Phase 5B — SES Transactional Email Design

Date: 2026-09-07
Branch: `feat/aws-native-phase-0-1`
Status: Design approved in chat; implementation pending written-spec review

## 1. Goal

Move Sea N Shore authentication email delivery onto Amazon SES using the approved sender `no-reply@seaandshore.in`, while keeping the current AWS staging application stable and avoiding any production DNS cutover.

Phase 5B covers the email delivery path used by Cognito for:

- new-account email verification codes;
- password-reset codes;
- future Cognito-generated account messages that use the user pool email configuration.

The phase also establishes the infrastructure contract that future application transactional email can reuse, but it does not add unused product email features merely to exercise SES.

## 2. Current state

The repository already has:

- a Cognito user pool in `infra/aws/app/auth.tf`;
- Cognito email verification enabled through `auto_verified_attributes = ["email"]`;
- account recovery through verified email;
- sign-up and forgot-password flows that call Cognito;
- an SES v2 configuration set named `${local.name_prefix}-transactional` in `infra/aws/app/email.tf`;
- AWS staging in `ap-south-1`;
- GitHub OIDC deployment and AWS verification workflows.

The repository does not yet have:

- an SES domain identity for `seaandshore.in`;
- Easy DKIM records for the domain;
- an SES sender policy for Cognito;
- Cognito configured with `EmailSendingAccount = DEVELOPER`;
- a verified custom sender in the live user pool;
- a checked SES production-access state for `ap-south-1`.

The current user-pool email path therefore relies on Cognito's default delivery behavior.

## 3. Approved architecture

The approved long-term email architecture is:

`seaandshore.in` authoritative DNS -> Route 53

`no-reply@seaandshore.in` -> SES verified domain identity -> SES transactional configuration set -> Cognito user pool

The domain registrar does not need to move as part of this phase. Only authoritative DNS is expected to move to Route 53 during the later controlled production cutover.

Phase 5B must not change production nameservers, website DNS, production traffic, Vercel availability, or the public Sea N Shore domain routing.

## 4. SES identity design

Create one SES v2 domain identity in `ap-south-1`:

- domain: `seaandshore.in`;
- DKIM: Easy DKIM;
- DKIM key length: AWS default/current recommended Easy DKIM behavior;
- sender: `no-reply@seaandshore.in`;
- configuration set: `sea-n-shore-staging-transactional` for staging;
- account-level suppression reasons remain `BOUNCE` and `COMPLAINT` through the existing configuration set.

The SES identity is domain-based rather than an individual-email identity so future senders on the same domain can be added without a second ownership-verification process.

No inbound-email receiving rules are part of Phase 5B.

## 5. DNS boundary

The current authoritative DNS provider is not yet known. Phase 5B must discover the live NS records before attempting DNS automation.

Two cases are supported.

### 5.1 Existing DNS is already Route 53

If an authoritative Route 53 hosted zone for `seaandshore.in` already exists in the AWS account, Terraform may manage the SES DKIM records in that hosted zone.

### 5.2 Existing DNS is external

If the authoritative nameservers are not Route 53, Phase 5B must not move the nameservers automatically.

Instead:

1. create the SES identity;
2. obtain the exact Easy DKIM CNAME records generated by SES;
3. record them in the deployment evidence;
4. add only those SES validation records through the current DNS provider if an authorized connector/API is available;
5. otherwise stop at the DNS boundary and present the exact records for one controlled manual DNS update.

The later production Route 53 migration remains a separate cutover step.

## 6. Cognito delivery design

Once the SES identity is verified, configure the existing Cognito user pool to use SES directly:

- `email_sending_account = "DEVELOPER"`;
- `source_arn` = the verified `seaandshore.in` SES identity ARN;
- sender shown to users = `Sea N Shore <no-reply@seaandshore.in>` where supported by the user-pool configuration;
- configuration set = the existing transactional SES configuration set;
- reply-to = `no-reply@seaandshore.in` unless a separate monitored support address is approved later.

Cognito remains responsible for generating verification/reset codes and message timing. Phase 5B changes the delivery provider and sender identity; it does not replace Cognito confirmation/reset logic with custom application code.

A sending-authorization policy must limit use of the SES identity to Cognito in the same AWS account and the Sea N Shore user pool. The policy must not grant public or cross-account send permission.

## 7. SES sandbox and production-access gate

SES production access is region-specific. Before switching Cognito to SES, the workflow must query the SES v2 account state in `ap-south-1`.

If production access is enabled:

- proceed with the Cognito SES cutover after domain verification.

If the account is still in the SES sandbox:

- do not switch the live staging user pool to a path that would prevent ordinary users from receiving confirmation/reset mail;
- request SES production access for the transactional use case;
- staging smoke tests may use only verified recipients or the SES mailbox simulator until production access is granted;
- keep Cognito's currently working email configuration in place until the gate passes.

This prevents an infrastructure migration from silently breaking signup or password recovery.

## 8. Terraform and current state-drift constraint

The application Terraform state currently contains a CloudFront-scoped WAF resource whose original `aws.us_east_1` provider alias is absent from current source. A normal full app `terraform plan/apply` is therefore not safe until the edge configuration is reconstructed.

Phase 5B must not solve this by deleting the WAF from state or destroying the live WAF.

Implementation will follow this rule:

- desired SES/Cognito configuration is committed to Terraform source;
- Terraform formatting and validation remain mandatory;
- no full app Terraform apply is run while the orphan-provider condition exists;
- live SES setup and, after all gates pass, the Cognito email update may be performed through a narrowly scoped GitHub OIDC operational workflow;
- every operational change must mirror committed Terraform intent so later Terraform reconciliation has one clear desired state;
- the edge/WAF source repair remains mandatory before a future unrestricted app-stack plan/apply.

For the Cognito update, the operational workflow must first describe the current user pool and preserve its existing mutable settings. It must not replace the user pool or reset unrelated settings.

## 9. IAM boundaries

### 9.1 Cognito

Cognito may send only through the verified SES identity and only for the Sea N Shore user pool. Use the AWS Cognito service principal and constrain the authorization policy by AWS account and user-pool ARN.

### 9.2 ECS application task role

Phase 5B does not grant the ECS application task role broad SES access because the application currently has no independent transactional-email feature that requires it.

When a real application email feature is introduced later, add a dedicated app mailer with least-privilege `ses:SendEmail` access to the approved identity. Do not pre-grant `ses:*`.

### 9.3 GitHub deploy/ops role

Any temporary Phase 5B operational workflow may use only the permissions required to:

- inspect SES account/identity state;
- create/read/update the approved SES identity and identity policy;
- inspect the existing Cognito user pool;
- update only the intended user-pool email configuration;
- inspect CloudWatch evidence where already permitted.

Do not broaden the role to general IAM or SES administration unless a specific AWS denial proves it is required.

## 10. Source changes

Expected repository changes:

- `infra/aws/app/email.tf`
  - add SES v2 domain identity;
  - add Cognito-specific SES identity policy;
  - keep the existing transactional configuration set;
  - expose/derive DKIM data needed for DNS verification where Terraform/provider support allows.

- `infra/aws/app/auth.tf`
  - add the desired Cognito SES email configuration, gated so it is enabled only after SES identity readiness is explicitly approved for the environment.

- `infra/aws/app/aws-native-variables.tf`
  - add explicit email-domain/from-address controls and a safe enable flag if needed for the two-stage cutover.

- `infra/aws/app/terraform.tfvars.example`
  - document non-secret SES configuration values.

- `.github/workflows/...` and/or `scripts/aws/...`
  - add a bounded Phase 5B verification/cutover workflow or script only if the current app-state WAF drift prevents Terraform from applying the committed desired state.

- tests under `scripts/aws` and/or `src` as appropriate
  - verify the source contract, sandbox gate, sender identity, least-privilege policy, and preservation of existing Cognito configuration.

No Supabase runtime changes are part of Phase 5B.

## 11. Two-stage rollout

### Stage A — SES readiness

1. Read the exact migration-branch head.
2. Run read-only AWS discovery:
   - authoritative nameservers for `seaandshore.in`;
   - SES production-access state in `ap-south-1`;
   - existing SES identities;
   - existing transactional configuration set;
   - current Cognito user-pool email configuration.
3. Add RED source-contract tests.
4. Add the SES identity/policy Terraform intent and supporting operational script if required.
5. Reach GREEN CI on the exact head.
6. Create/verify the SES domain identity without changing public website routing.
7. Publish only SES DKIM verification records at the current DNS provider.
8. Wait until SES reports the identity/DKIM as verified.
9. Confirm production access state.

### Stage B — Cognito cutover

Only after Stage A is verified and production access is enabled:

1. add/enable Cognito `DEVELOPER` SES configuration in committed source;
2. prove RED then GREEN tests for the cutover contract;
3. run exact-head CI;
4. update the live staging user pool through the safe Terraform path, or the bounded operational workflow if the known WAF state issue still prevents app Terraform;
5. verify the user pool now reports the approved source identity/configuration set;
6. exercise sign-up email confirmation with a controlled address;
7. exercise forgot-password/reset email delivery with a controlled account;
8. confirm both emails arrive from `no-reply@seaandshore.in`;
9. review SES sending statistics and CloudWatch/application logs for errors.

## 12. Message content

Phase 5B keeps Cognito's verification-code and password-reset behavior intact.

If message text is customized during implementation, it must remain simple and functional:

- verification subject: `Verify your Sea N Shore email`;
- reset subject: `Reset your Sea N Shore password`;
- never include passwords;
- never log verification or reset codes;
- never expose whether an arbitrary reset-request email belongs to an account.

Custom HTML branding is not required to declare Phase 5B complete. Reliable delivery and correct sender authentication come first.

## 13. Error handling and observability

Operational scripts must fail closed when:

- SES identity is not verified;
- DKIM verification is incomplete;
- SES production access is not enabled for the intended unrestricted-recipient smoke test;
- the current Cognito user-pool state cannot be read;
- the intended sender identity ARN does not match `seaandshore.in`;
- an update would alter unrelated Cognito settings.

Logs may include:

- SES identity name/ARN;
- verification status;
- DKIM status;
- configuration-set name;
- Cognito user-pool ID/ARN;
- SES production-access boolean;
- message IDs from controlled smoke sends.

Logs must not include:

- passwords;
- verification/reset codes;
- OAuth secrets;
- database secrets;
- Supabase keys;
- full authentication tokens.

## 14. Test strategy

### RED contracts

Tests should prove the repository initially lacks the required Phase 5B behavior, including at minimum:

- no SES domain identity for `seaandshore.in`;
- no Cognito `DEVELOPER` SES email configuration;
- no Cognito-scoped SES sending policy;
- no safe readiness gate for SES sandbox/identity state.

### GREEN contracts

After implementation, tests must verify:

- exact approved sender/domain;
- Easy DKIM domain identity exists in desired source;
- configuration set is attached to the Cognito email configuration;
- authorization policy is constrained to Cognito/account/user pool;
- no wildcard `ses:*` application permission is introduced;
- sandbox/readiness checks block unsafe cutover;
- current auth action semantics for sign-up confirmation and password reset remain unchanged;
- Terraform format/validate and existing application CI stay green.

## 15. Live verification evidence

Phase 5B is complete only when fresh evidence shows:

- `seaandshore.in` is a verified SES identity in `ap-south-1`;
- DKIM status is successful;
- SES production access is enabled for `ap-south-1`, or the environment is explicitly limited to verified-recipient staging with Cognito cutover deferred;
- Cognito staging user pool reports SES `DEVELOPER` delivery with the approved identity/configuration set;
- a controlled sign-up confirmation email is received;
- a controlled password-reset email is received;
- sender is `no-reply@seaandshore.in`;
- existing authentication, Home/feed, S3 media, Aurora, and ECS health checks remain healthy;
- no repeating new runtime/email errors appear in CloudWatch.

## 16. Rollback

If the SES/Cognito cutover causes delivery problems:

1. revert the Cognito user pool email configuration to the previously captured working configuration;
2. leave the SES identity and DKIM DNS records in place unless they themselves are incorrect;
3. do not delete user accounts or authentication data;
4. do not alter production website DNS;
5. verify sign-up/reset delivery again using the restored Cognito configuration.

Rollback must not require database changes.

## 17. Explicit non-goals

Phase 5B does not:

- move production authoritative DNS to Route 53;
- transfer the domain registrar;
- change production website DNS;
- decommission Vercel;
- remove Supabase packages/runtime remnants;
- implement marketing/bulk email;
- implement SES inbound email;
- create newsletters;
- add an unused general-purpose application email subsystem;
- repair or delete the orphaned CloudFront/WAF state resource;
- merge to `main` or create a pull request.

## 18. Completion rule

Do not call Phase 5B complete based only on Terraform/source state. Completion requires verified SES identity/DKIM, safe Cognito email configuration, successful controlled sign-up and password-reset delivery, and fresh AWS health/log evidence.
